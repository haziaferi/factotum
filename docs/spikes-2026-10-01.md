# Spikes, 2026-10-01: SPEC §9.2, §9.4, §9.6

These are the three checks that needed no layout decision. Every result below was measured this session. The commands to reproduce them are listed under each spike.

## §9.2 Planner rules through Factotum's stored form

`python tools/spikes/planner_check.py` ports Tendril's planner (`CalendarSchedule.kt:236-371`) and compares it with Factotum's stored form. The RRULE side is expanded with `tools/recurrence_sim.py`, the engine contest 04 was scored with. The window is 8 weeks from 2026-09-21.

### Part 1: rules that ADR 06 said map to RRULE

The table gives missing and extra occurrences against Tendril.

| Rule | Tendril occurrences | literal DTSTART (ADR 06 as written) | aligned DTSTART |
|---|---|---|---|
| Daily 07:00 | 56 | 0 / 0 | 0 / 0 |
| Once | 1 | 0 / 0 | 0 / 0 |
| Mon, Wed, Fri until 1 Nov | 18 | 0 / 0 | 0 / 0 |
| Every 3 days, window starting before the anchor | 19 | **3 missing** | 0 / 0 |
| Every 3 days, activeFrom off the anchor's grid | 14 | **14 missing, 14 extra** (a shifted grid) | 0 / 0 |
| Every 2 weeks, Mon and Thu, anchored on a Wednesday | 8 | **3 missing** (the anchor week's Monday) | 0 / 0 |
| Every 3 hours, 07:30–22:00 | 280 | 0 / 0 | 0 / 0 |
| 3 a day at 07:30, 12:00, 19:15 | 168 | single RRULE: **336 extra** (BYHOUR × BYMINUTE) | RULE_SET: 0 / 0 |

Findings, which amend ADR 06:
- **DTSTART is the first date on or after `activeFrom` that the rule's own anchor allows**, not `activeFrom` itself. For EveryNWeeks it is the Monday of an aligned week, because Tendril counts weeks Monday to Monday (`CalendarSchedule.kt:290`).
- **Several set times a day are a RULE_SET** (ADR 04), with one RRULE per time, whenever the times' minutes differ.
- **Occurrences before a habit exists aren't carried over.** Tendril's `floorMod` also shows occurrences before the anchor (`:288`). In Factotum, DTSTART is aligned on or after the later of `activeFrom` and the day the habit was created.

### Part 2: PLANNED round trip

500 random weeks were generated, each with 1–3 fixed habits as load, 1–3 "n times a week" habits, sometimes a block-slot "n times a day" habit, pauses, and confirmed weeks stored as ADR 11 WEEK edits. Each week was written to Factotum rows, read back and planned again.

| Columns | Identical plans |
|---|---|
| only the ADR-declared item columns | **0/500** |
| plus `block_id` only | 0/500 |
| plus `duration_min` only | 0/500 |
| **plus both** | **500/500** |

Finding, which amends ADR 06: a HABIT item needs **`block_id`** (its default time block, Tendril's `Habit.blockUid`) and **`duration_min`** (Tendril's `Habit.duration`).
- The planner places a habit with no set time in its block.
- The planner balances the week by minutes (`CalendarSchedule.kt:314-341`).
- Neither column was declared for habits. ADR 02 keeps end times on EVENT only.

## §9.4 Seeded random draws

`tools/spikes/seeded_draw/Draw.java` and `Uniform.java` run on Java 21 against the real `kotlin.random` code. They draw 1,000 RANDOM_DAYS occurrences and 700 RANDOM_WINDOW times, then check uniformity over 10 × 100,000 draws.

| Check | Result |
|---|---|
| Same draws across Kotlin stdlib versions | **18/18 identical**, from 1.8.21 to 2.4.10. One more jar in the cache was a javadoc jar with no classes, so it isn't counted. |
| Same draws across default time zones (Rome, New York, Kolkata, UTC) | **identical**. The seed uses local dates, not instants. |
| Two items with the same start and range drawing the same day | Chronicle's seed today (`RepeatSchedule.kt:39`, no item in it): **1000/1000**. ADR 04's seed (item id + occurrence date): 239/1000, chance being 250. |
| Uniformity, χ² at 5% | `kotlin.random` 0/10 batches fail; SplitMix64 0/10 |
| RANDOM_WINDOW draws that fall in the 2027-03-28 spring-forward gap (Rome, 01:00–04:00 window) | 20/700. `java.time` moves them forward an hour, the same way on every device. |

Decisions for the SPEC. They are fixes, not owner questions:
- **The seed** is FNV-1a 64 of the UTF-8 string `itemId|occurrenceDate|kind`.
- **The generator** is SplitMix64, written into Factotum (about 20 lines). `kotlin.random` has been stable across 18 versions, but its documentation leaves room for the algorithm to change between Kotlin versions, and two devices on different app versions must still agree.
- **A drawn time in a DST gap** moves forward by the gap, as `java.time` does. In a repeated hour, the earlier offset is used. Times are local ("floating"), so a device in another time zone rings at the same local time.

## §9.6 llama.cpp licence

**MIT, and nothing else is shipped.**
- Equipoise builds `llama` and `ggml` with `LLAMA_BUILD_COMMON`, `TOOLS`, `TESTS`, `EXAMPLES` and `SERVER` all off (`app/src/main/cpp/CMakeLists.txt:12-24`).
- The vendored extras link only through `common` and `tools/mtmd`: cpp-httplib, nlohmann, miniaudio, stb, sheredom and the hash code (`common/CMakeLists.txt:132,147`; `tools/mtmd/CMakeLists.txt:84`). Neither is built.
- A licence grep over `src/`, `include/`, `ggml/include` and the CPU backend found only operating-system names, not licences. KleidiAI, SYCL and OpenVINO carry other notices, but they are off or not built.

**Obligation:** ship the llama.cpp copyright and MIT permission notice (`third_party/llama.cpp/LICENSE`) in the app, for example on an open-source licences screen. **For the Windows build:** the same `CMakeLists.txt` switches must be kept, so the vendored extras don't creep in.
